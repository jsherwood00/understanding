A.1  [CRITICAL] PERCENTILE CALIBRATION INCLUDES HOLDOUT-TOPIC STORIES
     pipeline/percentile_calibrate.py:54-62

  files_for() uses globs:
      reply scope:   "{emotion}_topic_*_split_train_story_*.npz"
      thought scope: "{emotion}_topic_*_split_train_thought.npz"

  The "_split_train_" qualifier filters the TRIAL-level split
  (within-topic train trials vs. trial-holdout trials 12-14). It
  does NOT filter the TOPIC-level split (train topics 0-79 vs.
  holdout topics 80-99). topic_split.json is NOT loaded anywhere
  in this file.

  Empirical confirmation (file counts in data/thinking/activations/):
                  matched by glob   train topics 0-79   holdout topics 80-99
      joy           1164              924                240
      sadness       1176              948                228
      anger         1200              960                240
      fear          1188              948                240
      disgust       1200              960                240
      surprise      1188              948                240

  ~20.0% of every emotion's calibration corpus came from holdout
  topics (80-99). The commit message for 1ae6549 explicitly claims
  "Source: contrastive corpus train-split (~130k samples per cell
  for reply scope, ~32k for thought), holdout intentionally
  excluded".  The CODE does not honor that claim.

  This is a pre-registration violation. The topic_split.json was
  committed at 8a6f5f7 (2026-05-10) with the explicit
  "locked_before": "any vector computation runs" stipulation, and
  compute_vectors.py honors it (pipeline/compute_vectors.py:177-179,
  :239-241). The percentile-calibration step was authored later and
  did not load topic_split.json.

  Impact: the breakpoint distributions in
  data/thinking/vectors/{reply,thought}/cutoff_50/calibration.json
  are partially built on activations from topics that are supposed
  to be held out. Any "percentile against training stories" claim
  is therefore actually "percentile against (training topics +
  holdout topics, train trials)". The y-axis label
  "Emotion intensity (percentile)" overstates the cleanness of the
  reference distribution.


A.2  [HIGH] "BEST LAYER PER EMOTION" SELECTED BY VECTOR NORM, NOT BY
     ACCURACY OR DISCRIMINABILITY
     pipeline/compute_vectors.py:362-394

  After writing each layer's vector, the code computes its L2 norm
  and picks the argmax-norm layer as "best":
      best_layer, best_norm = max(rows, key=lambda r: r[1])
      best[E] = {"layer": best_layer, "norm": best_norm}

  Empirical consequence: every emotion in every scope picks the
  same single layer because the residual-stream norm grows
  monotonically (or otherwise dominantly) at one layer position:
      data/thinking/vectors/reply/cutoff_50/best_layer_per_emotion.json:
          joy/sadness/anger/fear/surprise/disgust → all layer 13
      data/thinking/vectors/thought/cutoff_50/best_layer_per_emotion.json:
          all six emotions → layer 32

  These selections disagree with the 6-way holdout-classification
  accuracy reported in the same directories'
  holdout_classification_topic_level.json:
      reply scope:   L13=0.379  L17=0.376  L21=0.324  L25=0.536  L28=0.290  (no L32 reported)
      thought scope: L13=0.487  L17=0.391  L21=0.185  L25=0.210  L28=0.176  L32=0.416

  The norm-selected "best" (reply=L13, thought=L32) is NOT the
  accuracy-best for either scope (reply=L25, thought=L13). The
  best_layer_per_emotion.json files are therefore misleading as a
  layer-quality signal.

  Notes:
   - lib/emotions.ts:36-42 hard-codes BEST_LAYER = {thought: 13,
     reply: 25}, which IS the accuracy-best (not the norm-best from
     the JSON). The frontend default is correct; the JSON file
     contradicts it.
   - The docstring at compute_vectors.py:27-30 does not document
     the selection criterion. A reviewer reading
     best_layer_per_emotion.json would have no way to know it's
     norm-based.


A.3  [HIGH] TRAINING-TIME CUTOFF NOT APPLIED AT INFERENCE OR
     CALIBRATION
     pipeline/compute_vectors.py:128-135 vs.
     pipeline/percentile_calibrate.py:77-91 vs.
     backend/inference.py:296-309 (_project)

  Vectors at data/thinking/vectors/<scope>/cutoff_50/ were computed
  from per-story mean residuals where the first 50 tokens of each
  story were excluded:
      compute_vectors.py:128-135
      return layer_arr[cutoff:].astype(np.float32).mean(axis=0)
      # called with cutoff=50

  At calibration time, percentile_calibrate.py:projections_from_file
  projects EVERY position of every NPZ:
      acts = data[f"layer_{L}"].astype(np.float32)
      out[L] = acts @ emo_vectors[L]
  No cutoff applied — positions 0..49 are included.

  At inference, backend/inference.py:_project projects the current
  last-position residual (whatever its position in the generated
  reply). No cutoff filter exists in the live path. The first
  ~50 reply tokens are projected against a vector that was trained
  to point in the direction of LATER-token averages.

  All three regimes use the same vectors but different position
  distributions:
    - vector training      : positions 50..N-1, averaged per story
    - calibration distrib  : positions 0..N-1, per token
    - inference distrib    : positions 0..N-1, per token (matches
                             calibration, not vector training)

  Inference and calibration are consistent with each other (so the
  y-axis percentile is empirically grounded), but neither is
  consistent with the vector-training distribution.


A.4  [HIGH] PROMPT-CONTEXT MISMATCH BETWEEN VECTOR EXTRACTION AND
     LIVE INFERENCE
     pipeline/extract_activations.py:209-241 vs.
     backend/inference.py:_build_prompt + generate_stream

  Vector / calibration extraction tokenizes the RAW story text and
  forwards it as a standalone input:
      pipeline/extract_activations.py:220
          input_ids = tokenizer(text, return_tensors="pt").input_ids[0]
  No chat-template wrapper, no user prompt, no <|channel> markers,
  no system tokens. The residual at NPZ row 0 is the residual at
  the FIRST token of the story text, with NO conversational context.

  Live inference applies the full Gemma chat template with
  enable_thinking=True (backend/inference.py:286-292):
      text = tokenizer.apply_chat_template(
          msgs, tokenize=False, add_generation_prompt=True,
          enable_thinking=True,
      )
  Then the model generates tokens in this conversational context.
  Generated reply/thought tokens are at high sequence positions
  (prompt + thinking + reply), with full KV-cache context.

  Implication: every saved residual in
  data/thinking/activations/ was computed from a forward over the
  story text alone. The live demo never sees that distribution —
  it always projects residuals that were produced under
  conversational context with the chat template fully consumed.

  Whether this is a meaningful distributional gap (and whether the
  emotion direction generalizes across the two contexts) is an
  empirical question; the code makes no claim that it does.


A.5  [HIGH] V2 (thinking_thought) RESIDUALS LIKELY EXPOSE LITERAL
     EMOTION WORDS BECAUSE NO LEAK FILTER IS APPLIED
     pipeline/compute_vectors.py:558-572 +
     pipeline/extract_activations.py:351-376

  The pre-registered synonym filter (commit 6cf25bf) is applied to
  emotion STORIES at vector-compute time and excludes any story
  whose text contains the prohibited word for that emotion. It is
  deliberately NOT applied to THOUGHT extractions:
      compute_vectors.py:558-561
          # Set 3: thinking, thought (leak filter not applied to
          # thoughts — the model's reasoning often quotes the emotion
          # word explicitly, which is fine for thought-level
          # analysis).
      extract_activations.py:372-374
          # Thoughts aren't constrained by the no-emotion-word rule

  The model's "thought" blocks for an emotion=joy batch routinely
  start with phrasings like:
      "Here's a thinking process: ... user wants a joyful story...
       must convey joy and unexpected delight..."
  i.e. the emotion word appears verbatim, repeatedly, in the
  thought.

  V2 vectors are therefore at least partly a direction along which
  "this text discusses emotion E" rather than "this text expresses
  emotion E". The Cohen's d numbers for V2 (Part B1 below) are
  3.07-4.27 vs. 0.98-1.38 for V1/V3 — consistent with a much
  easier discriminative task (presence of the emotion word in the
  text vs. emotional content per se).

  This is not, on its own, a bug. The docstring at
  compute_vectors.py:558-572 acknowledges the choice. It IS a
  research-validity concern if any claim is made about V2 being a
  "feeling" direction rather than a "discussing the emotion"
  direction.


A.6  [MED] CALIBRATION SAMPLES ARE PER-TOKEN; VECTOR TRAINING SAMPLES
     ARE PER-STORY MEAN
     pipeline/percentile_calibrate.py:77-91 vs.
     pipeline/compute_vectors.py:128-135

  Vectors are computed as the contrastive difference between
  per-story mean residuals. Each "training data point" is one
  story's mean residual at one layer.

  Calibration breakpoints are computed by projecting EVERY token
  in every train-trial NPZ. Each "calibration data point" is one
  token's residual at one layer.

  The two distributions have different shapes (per-token has much
  higher variance than per-story-mean). The percentile lookup at
  inference therefore answers "what fraction of training-corpus
  tokens projected lower than this", not "what fraction of training
  stories had a mean projection lower than this". The y-axis label
  "Emotion intensity (percentile)" does not specify the unit.


A.7  [MED] V1 (no_thinking_full) HAS NO CALIBRATION FILE BECAUSE THE
     CALIBRATOR HARDCODES THE THINKING CORPUS PATH
     pipeline/percentile_calibrate.py:46

      ACTIVATIONS_DIR = DATA_DIR / "thinking" / "activations"

  files_for() never accepts a corpus argument. If someone runs
  `python -m pipeline.percentile_calibrate --scope reply` intending
  to calibrate V1 vectors, the script silently reads V3 activations
  (since V3 reply files also match the glob in data/thinking/) and
  writes the result to data/thinking/vectors/reply/cutoff_50/.
  V1's directory at data/no_thinking/vectors/full/cutoff_50/ has
  no calibration.json on disk.

  Practical consequence: the live demo cannot use V1 vectors as-is.
  Part B3 below estimates V1 accuracy using an inline-computed
  percentile reference (Part B's audit script,
  empirical_breakpoints_from_train), but no saved calibration
  artifact exists for V1.


A.8  [MED] FIRST GENERATED TOKEN'S PROJECTION IS BASED ON THE PROMPT'S
     LAST-POSITION RESIDUAL, NOT ON A GENERATED-POSITION RESIDUAL
     backend/inference.py:419-475

  Trace of the loop per the comments + read of the actual code:
    1. First _step processes the full prompt; hook captures the
       residual at every prompt position.
    2. Loop iter 0: next_id is the first sampled token. self._captured
       still holds prompt-residuals from step 1. _project takes
       self._captured[layer][0, -1, :] — the residual at the LAST
       position of the prompt. This residual produced (via the LM
       head) the sampled token. So semantically it is "the state
       that emitted this token" — defensibly aligned with training.
    3. Iter 1 onwards: hook captures the residual at the just-
       processed generated token's position; _project reads it.

  The first reply-phase token's projection uses a residual at a
  PROMPT position. The training corpus (NPZ files in
  data/thinking/activations/) was built from forwards over story
  text ALONE (no prompt — see A.4). So the training distribution
  contains no analog of "residual at prompt's last position".

  After token 0 of each phase, the inference distribution matches
  what the model sees during a story re-forward.


A.9  [MED] CHANNEL-MARKER TOKENS ARE PROJECTED BEFORE BEING
     SUPPRESSED FROM EMIT
     backend/inference.py:431-475

  The order in the per-iteration block is:
    1. Detect channel marker (lines 431-438), switch phase.
    2. Project with NEW phase (line 455).
    3. Decide suppression (line 464).
    4. _step on this token (lines 470-475).
    5. Yield (line 487) — skipped if suppress_emit is True.

  When the model emits <|channel> (token_id == self.channel_open_id),
  phase flips to "thought" and the captured residual (from the
  previous _step, i.e. the residual that produced the marker
  token) is projected against V2 thought vectors. The yielded
  event is suppressed for the user, but
    a) the projection computation runs (cheap waste);
    b) the SAME captured residual was the one used to PRODUCE the
       marker, so "what phase did this residual belong to?" is
       arguably "reply" (the residual that decided to switch into
       thought mode), not "thought".
  The first emitted thought-content token after the marker uses
  its OWN residual (which is genuinely a thought-phase residual),
  so the user-visible reading is not contaminated.

  Same logic applies symmetrically at <channel|>: the reply-phase
  projection that the user first sees is of the genuine first
  reply-content token's residual; the suppressed projection of
  the close-marker is computed but not shown.


A.10 [MED] BACKEND HARDCODES cutoff_50 AND USES THE DENOISED COPY
     WITHOUT METADATA-LEVEL VERIFICATION
     backend/inference.py:64

      return DATA_DIR / "thinking" / "vectors" / scope / "cutoff_50"

  compute_vectors.py writes both
      data/.../<scope>/cutoff_{N}/      (denoised — projected
                                         orthogonal to neutral PCs)
      data/.../<scope>/cutoff_{N}_raw/  (raw — no PC projection)
  at three cutoffs each. The backend silently picks the denoised
  copy at cutoff_50. There is no metadata file in either directory
  recording which cutoff this is, whether it's denoised, what date
  the vectors were computed, or which git commit produced them.

  No code-level cross-check ensures vectors_dir(scope) actually
  contains cutoff_50 vectors (vs. e.g. a manual file move).


A.11 [MED] "WITHIN-CELL HOLDOUT" NAMING IS AMBIGUOUS AND ITS
     COMPOSITION IS NOT GENERALIZATION
     pipeline/validation.py:135-146 + 137-142

  validation.py defines three holdout modes:
    "within_cell"  — train topics (0-79) × trial-holdout trials (12-14)
    "topic_level"  — holdout topics (80-99) × all trials
    "all"          — union

  The phrase "within_cell" is ambiguous between
    (a) "within the same (emotion, topic) cell that produced training
        trials" and
    (b) "within the cell of train-topics".
  The docstring at line 102-107 clarifies it means (b). For a
  reviewer this is fine, but the JSON output file
  holdout_classification_within_cell.json could be misread as a
  measure of "within-distribution" accuracy when it is actually a
  measure of "within the same topics that the model was trained on,
  testing held-out trials".

  The headline 53.6% (V3 / topic-level) and 96.7% (V2 / B3 below)
  numbers should be compared only against topic_level, not
  within_cell.


A.12 [MED] best_layer_per_emotion.json AND cosine_matrix.json FILES
     ARE COMPUTED AT THE SAME "COMMON BEST" LAYER, COUPLING TWO
     UNRELATED SELECTIONS
     pipeline/compute_vectors.py:396-409

  After picking the per-emotion norm-best layer, the code chooses a
  single "common best" layer as the mode of those norm-bests:
      common_best = Counter(b["layer"] for b in best.values()).most_common(1)[0][0]
  and writes the 6x6 cosine matrix at that ONE layer. Because all
  six emotions pick the same layer (per A.2), this is a single-
  layer matrix.

  Effect: cosine_matrix.json reports cosines at the norm-best
  layer, which is NOT the accuracy-best layer. A reviewer reading
  cosine_matrix.json sees angles between vectors at a different
  layer than the one used for classification/visualization.

A.14 [LOW] PCA OFF-BY-ONE — INVESTIGATED, NOT A BUG
     pipeline/compute_vectors.py:333

      k = int(np.searchsorted(var_explained, var_target) + 1)

  FALSE POSITIVE FROM SUBAGENT. Verified empirically with a worked
  example. searchsorted with side="left" (default) returns the
  leftmost insertion index. With +1, the formula returns the
  smallest k such that var_explained[k-1] >= var_target, which IS
  the intended "keep enough PCs to explain at least var_target of
  the variance" semantic. The trailing print statement
      f"layer {L}: kept {k} PCs explaining {var_explained[k-1]:.2%} ..."
  agrees with this interpretation.

B8.  INFERENCE PATH CODE TRACE
================================================================

This section traces the exact code path from `POST /chat` to a
yielded SSE event with `displayed percentile values`.

1. ENTRY: backend/main.py:104-136
   `@app.post("/chat")` calls `_engine.generate_stream(message,
   history)`, wrapping each yielded dict in `sse_starlette`
   `EventSourceResponse`.

2. PROMPT CONSTRUCTION: backend/inference.py:_build_prompt
   (lines 285-308)
   - msgs = [{role: user, content: text}], prefixed with history.
   - text = tokenizer.apply_chat_template(msgs,
                                          tokenize=False,
                                          add_generation_prompt=True,
                                          enable_thinking=True)
   - input_ids = tokenizer(text, return_tensors="pt").input_ids.to(device)
   - NOTE: this is the chat-template prompt; pipeline/
     extract_activations.py does NOT apply this template.

3. INITIAL FORWARD: backend/inference.py:419-421
       next_id, past_key_values = self._step(input_ids, None,
                                             do_sample=True)
   - self._step (lines 367-390) calls self.model(input_ids,
     past_key_values=None, use_cache=True).
   - During this forward, registered hooks on
     self.layers[L] for L in TARGET_LAYERS = [13, 17, 21, 25, 28, 32]
     (line 38) fire and write to self._captured[L] the layer's
     output[0] (the residual stream after layer L).
   - Hooks were attached in _attach_hooks (line 246-260) on
     self.layers = self.model.model.language_model.layers
     (line 145) — direct indexing into Gemma's 42-layer stack.
   - Layer indexing convention: 0-indexed integers into the
     HF layer list. pipeline/extract_activations.py uses the same
     0-indexed integers (extract_activations.py:228 — nnsight
     attribute path also indexes into .layers[L]). The
     calibration JSON keys are string-form integers
     ({"13": ..., "17": ...}); the live backend re-stringifies
     L when looking up (inference.py:298). Mapping is consistent.

4. GENERATION LOOP: backend/inference.py:423-495.
   Per iteration, with self._captured containing the most-recent
   forward's hidden states:

   a. Stop check (line 424-425): break if next_id in
      self.stop_token_ids = {eos, <turn|>, <end_of_turn>} (line
      154-162).

   b. Channel marker detection (lines 431-438):
        if next_id == self.channel_open_id   → phase = "thought"
        elif next_id == self.channel_close_id → phase = "reply"
      Phase starts at "reply" (line 412), is updated in-place.

   c. Decode (lines 442-447): generated_ids.append(next_id), then
      tokenizer.decode(generated_ids, skip_special_tokens=True).

   d. PROJECTION (line 455):
        all_raw = self.project_all_layers_raw(scope=phase)
      → calls self._project(scope, L) for L in TARGET_LAYERS.

      _project (lines 296-309):
        hidden = self._captured[layer]               # (1, seq_len, 2560)
        last = hidden[0, -1, :].to(torch.float32)    # (2560,)
        vecs = self.vectors[scope][layer]            # (6, 2560)
        scores = (vecs @ last).cpu().numpy()         # (6,)
        return {emo: float(scores[i]) for i, emo in enumerate(EMOTIONS)}

      `last` is the residual at the LAST position of whatever
      forward most recently fired the hook. For step 0 of the
      loop, that is the prompt's last position. For subsequent
      steps it is the previously generated token's position.

      No cutoff filter. No averaging within the projection step.

   e. NORMALIZATION (lines 456-459):
        all_thinking = {str(L): self._normalize(all_raw[L], phase, L)
                        for L in TARGET_LAYERS}

      _normalize (lines 326-368):
        - Picks bp = self._bp_cache[scope][layer][emo] when
          available (cache built at __init__ from
          calibration.json — lines 205-235).
        - Computes pct = float(np.interp(val, bp,
                                         PERCENTILE_GRID))
          where PERCENTILE_GRID = np.linspace(0, 100, 101) (line 70).
        - Clamps via max(0, min(100, pct)).
